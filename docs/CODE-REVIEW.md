## 二、未来发展方向（按价值排序）

### D1. --online 模式：漏洞库聚合（dependency-scout 方向）
- **能力**：远程预检时联网查 OSV API（漏洞库），把"依赖树扫描"升级为"漏洞扫描"
- **价值**：补上最大的安全缺口（已知漏洞）
- **成本**：中（OSV API 免费，JSON 解析）
- **风险**：联网需用户显式开启（--online），保持默认离线

### D2. LLM 深度解读报告（plugin-auditor 方向）
- **能力**：我们的 JSON 报告 + LLM 生成"人类可读的深度分析"（为什么红、风险场景、修复优先级）
- **价值**：让确定性规则输出对非技术用户更友好
- **成本**：低（我们 JSON 已结构化，LLM 消费零改造）
- **形态**：可作为独立 skill 或 dsh 工具增强，不破坏零依赖

### D3. 规则按维度拆分（维护性）
- **能力**：scanner.js 拆为 loader-scanner / security-scanner / packaging-scanner
- **价值**：规则 >20 条后保持可维护
- **触发**：规则数量到 20 时做（当前 15 条不急）

### D4. 版本追踪自动重审（之前讨论的 #2）
- **能力**：记录上次 clone commit，重测对比"有无变化"，变化时提示重审
- **价值**：解决"结果过期"（v0.12.2 的 commit 标注是基础）
- **成本**：低（报告已带 sourceCommit）

### D5. 插件健康指数（综合评分）
- **能力**：把 🔴🟡🟢 + freshness + dormancy + 依赖树 → 单维分数（0-100）
- **价值**：market 场景（dsh-mall 式）可排序比较
- **成本**：低（已有全部输入）
- **注意**：分数要透明（给分解），避免 dsh-mall 的"黑盒评分"问题

### D6. 审计结果作为 market 数据源
- **能力**：我们的 --json 输出可被 dsh-mall 类市场消费（"已验证"徽章）
- **价值**：生态位：审计 = 市场的质检层
- **成本**：接口已就绪（JSON schema v1）

### 路线图建议

```
短期（v0.13）：D1 漏洞聚合（--online）或 D4 版本追踪
中期：D2 LLM 解读 + D5 健康指数
长期：D6 生态位（market 质检层）+ D3 规则拆分
```
